# 0007: Every release we have, not a time window

## Context

[ADR 0006](0006-list-vendors-before-their-feeds.md) kept the Android and SteamOS adapters to the last 180 days so that the dial, which widened to 52 weeks whenever the oldest release was more than 26 weeks old, stayed at 26 weeks, and so that the timeline did not fill with old device builds. The cost was that the Release timeline showed one Android release and two SteamOS ones, although the source pages and the recorded fixtures hold many more. The timeline is meant to list every release the site has for each vendor.

## Decision

- The Android and SteamOS adapters emit every release they can read, newest first. For Android that means every row with a three-part tag and a dated build id, which in practice is Android 8 (2017) onward. The time window and `WINDOW_DAYS` are gone. The safety bounds stay: Android reads at most 2 MB and 5000 table rows, SteamOS at most 500 news items, the merge keeps the newest 1000 releases of each source (`MAX_RELEASES_PER_SOURCE`, applied only where lists are merged, never inside an adapter, so one large source cannot push another's rows out, and the snapshot script fails instead of dropping rows), and a row or post dated more than a day ahead of the clock is refused. Security-only `android-security-*` rows are still skipped: they carry a bare numeric build id and no Android version, and the release contract has no stage for them, so there is no clean way to show them. Older rows are skipped too, because they carry no date: two-part tags such as `android-4.4_r1` fail the tag pattern, and pre-Oreo build ids such as `NJH47F`, `KTU84P` and `FRF91` fail the build pattern and have no patch level to fall back on. The live history therefore starts at Android 8, not 2009.
- The dial no longer reads the data's span. Its window is fixed at 26 weeks, and notches are chosen by date, so older releases are neither drawn nor counted however wide the data is.
- The timeline lists everything it is given, grouped by month with the year, and counts per filter. It draws the 12 newest months that have releases and adds 12 more per "Show older" press, so the full history stays reachable without building every row at once.
- `src/data/releases.json` gains the history that is already recorded in the repository, and nothing else. The Android rows are the 21 release rows of `tests/fixtures/google/build-numbers.html` older than `android-17.0.0_r1` (`android-16.0.0_r1` to `r4` and `android-15.0.0_r20` to `r36`), and the SteamOS rows are the 17 other SteamOS posts of `tests/fixtures/valve/getnewsforapp-steamos-titles.json`, made by the adapters' own rules (id, stage, date and build as `parse` derives them (the Android snapshot dates follow the amended rule below only after its next refresh); the fixture has no post links, so the news page is the link). Older AOSP history is not in the repository; the live API serves it once deployed, and `node deploy/snapshot_releases.mjs` brings it into the snapshot.
- Apple, MikroTik and Windows are unchanged: the Apple feed and the Windows tables carry no window, and MikroTik publishes one line per channel.

## Consequences

- The Android and SteamOS history grows with each refresh of the snapshot and with the live feed; the live Android timeline reaches back to 2017 (Android 8), so it will be long. The home page still lists the newest five per family.
- Dating rule amended: a row is dated by the day in its build id unless its security patch level falls in a later month, in which case the patch level is used (and the patch level alone when the build id has no valid day). This applies to any row whose patch level is in a later month, not only branch builds: an older launch build such as `OPM1.171019.011` (patch level 2017-12-05) is dated by its patch level too. Branch builds such as `android-15.0.0_r24` (`BD4A.240925.111`, patch level 2025-01-05) are therefore dated 2025-01-05, not 2024-09-25, while `android-15.0.0_r25` (`BD4A.250405.003`, patch level 2025-02-05) keeps 2025-04-05. This supersedes the build-id-only dating that ADR 0006 and the earlier text of this ADR accepted. The snapshot dates change at its next refresh.
- Supersedes the window part of ADR 0006 (the Bounds paragraph of the Android section, the snapshot sentence that follows it, and the SteamOS bounds) and its Dates bullet and the date clause of its Format bullet (build-id-only dating). The rest of ADR 0006 stands.
- The dial's 52-week widening is removed. A wider dial would be a new decision.
- The fetch volume, the allowlist and the cache are unchanged.
