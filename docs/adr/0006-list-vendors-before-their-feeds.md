# 0006: List a vendor before its feed is connected

## Context

MikroTik (RouterOS), Google (Android), Microsoft (Windows) and Valve (SteamOS for the Steam Deck) were asked for next to Apple. Research for each found candidate sources, but when this change was prepared none of them could be read from the build environment except a few Android developer pages, and those hold HTML tables for pre-release builds only. No feed layout, channel label, version or build format, cadence or term of use was confirmed for the other three. Most of the release lists that did turn up came from search summaries and third-party news pages, which disagree with one another in places. An adapter written against a guessed layout would either fail quietly or publish a wrong "latest" version, and a stale pre-release table would have shown an Android beta from last year as the newest Android.

## Decision

The four families are added everywhere a family appears: the config with an accent that meets the contrast rules in all three themes, a card and a section with a drawn device on the front page, a ring on the dial, a chip on the timeline, an option on the compare page, and the notices and source links of every page. No adapter is registered and no release row is added to the snapshot. A family without releases already renders its empty state ("No release yet"), and the Worker fetches nothing for it.

The source link of each vendor in `families.json` is where a reader goes for that vendor's own release information. It is a link, not a fetch: the Worker's allowlist is the adapter's `urls`, and there is none.

An adapter is added for a vendor only when all of these hold, in a session that can reach its host:

- the real document has been fetched and a recorded sample is committed under `tests/fixtures/`;
- the format, the channel labels (a pre-release must map to `beta` or `rc`) and the version and build shapes are written down from that sample;
- the terms of use allow automated polling, and the poll interval, cache and User-Agent follow them;
- the parser is strict, skips malformed entries, keeps only https links on the vendor's hosts and copies no release notes.

## Consequences

- The site never shows a number that was not read from the vendor.
- Connecting a vendor later is one adapter file, one registry line, a fixture and a snapshot refresh; the pages, colours, filters and dial need no change.
- Until then the four platforms look empty. The About page says so. (Superseded: all four have adapters now, see the 2026-10-12 updates below; a family with no release in the data still shows the empty state.)
- Provenance of the source links. The four links below are the vendors' own landing pages for release information, shown as where to look. None was fetched and read when this change was prepared (mikrotik.com answered 403 to the research), so they are unverified: <https://mikrotik.com/download/changelogs>, <https://developer.android.com/about/versions>, <https://learn.microsoft.com/en-us/windows/release-health/release-information> and <https://store.steampowered.com/news/app/1675200>. Each must be checked by hand before its adapter lands, and the host lists in `families.json` stay at the single source host until then.
- SteamOS was listed but showed no releases until a verified Steam source and adapter existed (see the SteamOS update below).
- Open questions per vendor: MikroTik (which feed carries the stable and long-term channels, and the channel labels), Android (a machine-readable source for stable releases and monthly patch levels, since the developer pages cover betas), Windows (a structured source on Microsoft Learn or the update history pages, and how hotpatch and out-of-band updates are labelled) and Valve (the shape and channel labels of the Steam news data for the Steam Deck app).

## Update 2026-10-12: MikroTik is connected

A read-only probe fetched each vendor source from a GitHub runner on 2026-10-12 and recorded status, content type, size, SHA-256 and an excerpt. It settled the MikroTik open questions, and the adapter `deploy/sources/mikrotik.js` is registered:

- `https://upgrade.mikrotik.com/routeros/NEWESTa7.stable`, `.../NEWESTa7.long-term` and `.../NEWESTa7.testing` answer 200 `text/plain` with one line, `<version> <unix-seconds>` (`7.24.5 1790691687`, `7.23.8 1791452776`, `7.25rc1 1790864328`). The channel is in the URL only.
- `https://download.mikrotik.com/routeros/latest-stable-and-long-term.rss` answers 200 `application/rss+xml` with items titled `RouterOS <version> [<channel>]`, linking `https://mikrotik.com/download?v=<version>`, dated by `pubDate`. It is not polled: it names the same versions as the stable and long-term files with a different date (for 7.23.8, the item is dated a day after the NEWEST timestamp), and a failure of it would fail the whole source. Its excerpt in the probe was a re-serialised form, not the raw bytes, so no fixture was kept.
- Not used: `NEWEST7a.*` answers 404, and the plain `NEWEST7.*` files answer a stale `7.12.1` and `0.00`, so neither is a source. `https://mikrotik.com/current.rss` redirects to a stable-only feed that the RSS above already covers.
- Channels map as follows: `stable` and `long-term` are `release`, with the channel kept in the title (`RouterOS 7.23.8 long-term`); `testing` carries `rc` or `beta` versions (`7.25rc1`) and is a pre-release with its iteration number. A pre-release's `version` is its number alone (`7.25`) with the full string (`7.25rc1`) kept as its build, title and id. A pre-release version in a stable channel, or a plain version in testing, is skipped as malformed.
- MikroTik has no build ids. A release's build is its version string, which the snapshot contract requires to be non-empty and which the build sigil hashes like any generic build.
- The date of a release is its NEWEST unix timestamp in UTC, the one date source. A timestamp more than a day in the future is not believed and the release is skipped. The link is always built from the version, never read from a document.
- The three NEWEST documents are fixtures under `tests/fixtures/mikrotik/`, copied from the probe excerpts.

The terms of use for automated polling of these endpoints were not part of the probe and are still to be confirmed by hand, and the gate above (terms allow automated polling) is open until the owner confirms them or accepts the exception here; the Worker asks each URL at most once per cache window with the site's User-Agent. The vendor's source link in `families.json` stays the changelogs page. Android, Windows and Valve remain as described above.

## Update: the Android adapter (2026-10-12)

A read-only probe fetched each vendor source from a GitHub runner on 2026-10-12. For Android it read <https://source.android.com/docs/setup/reference/build-numbers> (status 200, `text/html; charset=utf-8`, 342,995 bytes, sha256 `77b4266e1122dc2495a65e2d93c38be3bd6a23715734a1affc5575c0036e8b7a`). The probe recorded the first three tables of the page. The second has the columns Build ID, Tag, Version, Supported devices and Security patch level, and lists AOSP release tags newest first, for example `android-17.0.0_r1` with build `CP2A.260605.016` and patch level 2026-06-05.

The Google adapter, `deploy/sources/android.js`, is connected on that basis:

- Format: the table is found by its header cells, not by its position, and read by a bounded scanner. One release per tag of the form `android-<major>.<minor>.<patch>_r<N>`; `version` is the tag's version part, `build` is the Build ID, `date` is the day in the build id's date segment (`CP2A.260605.016` is 2026-06-05) and the security patch level only when the build id has none.
- Stage: the recorded rows include no pre-release tag, so every row is a `release`, and the adapter skips any tag that is not of the release form (a beta tag, say) instead of guessing. The probe cut table 2 at 6,000 characters, so the whole page was not read.
- Security refreshes: the `android-security-*` rows have a bare numeric build id and are security-only. The release contract has no stage for them, so they are skipped.
- The link of every release is the build-numbers page, https on `source.android.com` only; `families.json` lists that host as the Google vendor's source, and the vendor's source link on every page now points at the build-numbers page (named "AOSP build numbers") because that is where the data comes from; `developer.android.com/about/versions` is no longer linked and stays unverified. No text of the page is kept.
- Ordering within a day: many tags share a build day, so the revision number is added as the time of day in seconds (`android-15.0.0_r36` is `00:00:36`), which keeps the higher revision first and the "latest" card on the newest revision. The shared merge breaks date ties by id as a string, which would put `r10` before `r9`.
- Bounds (the 180-day window below is superseded by [ADR 0007](0007-full-history-not-a-time-window.md): every row is now emitted): the page reaches back to 2009 (about three hundred release tags). Only rows dated within 180 days of the clock and of the newest row are emitted (the newest row is always kept, so the source is never empty), and a row dated more than a day after the Worker's clock is refused (a typo such as `CP2A.990605.016` must not pin a release in 2099). Without the window the live dial would widen to 52 weeks (it does so when the oldest release is more than 26 weeks old), and the timeline and the Android recent list would fill with old device builds. To show all of AOSP history, raise `WINDOW_DAYS` knowing the dial then shows 52 weeks.
- Dates: `date` is the build-cut day from the build id, not the day the tag was published (`android-15.0.0_r24`, build `BD4A.240925.111`, is dated 2024-09-25 although its patch level is 2025-01-05), so the order on the dial can differ from tag order. This is accepted. (Superseded by [ADR 0007](0007-full-history-not-a-time-window.md): a later patch-level month now dates the row.)
- The scanner skips the content of `script`, `style`, `template` and `textarea` elements and reads a tag name only when a space, `/` or `>` follows it (`<table-x>` is not a table). It still ends a tag at the first `>`, even inside a quoted attribute, and fails closed: a change of markup that breaks the table gives no rows, and the Worker then serves the snapshot as stale.
- The adapter sets its own `accept` (`text/html, application/xhtml+xml;q=0.9, */*;q=0.1`): the Worker sends a per-source `Accept` header, the feeds-and-text default for sources that set none.
- The fixture is an excerpt of the probe's raw tables. The probe's raw excerpt stopped at 6,000 characters part-way through the `android-15.0.0_r17` row; the fixture keeps the complete rows up to and including `android-15.0.0_r20`, so older rows are not in it.
- (Superseded by ADR 0007: the snapshot now holds the whole recorded history.) The snapshot held `android-17.0.0_r1` only, the one row inside the dial's 26-week window. The Worker serves the live rows within the 180-day window described above, merged with the snapshot; older rows are not emitted. The snapshot's `fetchedAt` is still the Apple refresh time.
- Open: the terms of use of the page have not been read for automated polling. The Worker reads it at most every ten minutes per Cloudflare location (the Cache API is per data centre) with the site's User-Agent, and the owner confirms the terms before the next release. The other three vendors are unchanged by this update.

## Update: the Windows adapter (2026-10-12)

Windows was the first of the four to meet the conditions above. A read-only probe fetched the pages from a GitHub runner on 2026-10-12 and recorded the answer of each (status, content type, size, SHA-256 and the raw tables). Both answered 200 `text/html` with no redirect:

- <https://learn.microsoft.com/en-us/windows/release-health/windows11-release-information> (132,531 bytes, SHA-256 `3c9fc9b33646c4ef971499c714960fc8718c6c1fef195da02c2ac94f69d20ceb`)
- <https://learn.microsoft.com/en-us/windows/release-health/release-information>, the Windows 10 page (320,848 bytes, SHA-256 `7a66752e80d19cacbf08ddfbefffa5588a69e7e2a70efcf130089fd903c0243c`)

Everything below is read from those records, and the recorded tables are committed under `tests/fixtures/microsoft/`:

- The first table of each page lists the servicing versions with the columns Version, Servicing option, Availability date, two End of updates columns, Latest update (Latest update for ESU on the Windows 10 page), Latest revision date and Latest build. The Latest update cell links to `https://support.microsoft.com/help/<KB>` with a label such as `2026-09 D` or `2026-09 OOB`. The second table is the LTSC table, whose end-date columns are named differently, and the adapter ignores it.
- The adapter emits one release per row whose servicing option is General Availability Channel: the family `Windows`, the version (`25H2`), the latest build (`26200.9550`), the latest revision date as midnight UTC, and the title `Windows 11 25H2 (2026-09 D)`. The stage is always `release`: these pages carry no pre-release channel, so nothing maps to `beta` or `rc`. The id carries the build, so each monthly update is a new entry once the snapshot merges.
- The families stay one `Windows` family, as the config has it. The title says 11 or 10, which the adapter reads from the page title; a later `Windows 11` and `Windows 10` family pair would be picked up without a code change.
- The contract has no end-of-support field, so a version whose End of updates cells all read "End of updates" says so in its title (Windows 10 22H2). A version still updated for some edition is not marked. A revision date more than a day ahead of the clock is refused (a typo such as 2099-01-01 would otherwise hold the Windows card and widen the dial); the clock is an optional argument, `now`, so the parser is still deterministic in tests.
- The link is the KB article only when it is `https://support.microsoft.com/help/<digits>` with no port or credentials, and otherwise the release-health page. `support.microsoft.com` is therefore added to the Microsoft vendor's `hosts`, which the pages use to accept a release link.
- The parser is a small strict scanner over the first table, bounded in input, rows and cell size, with no DOM and no `eval`. A page whose first table lacks the expected headers yields nothing, and the Worker then serves the last good copy.

Not settled by the probe: Microsoft's terms of use for automated reads of Microsoft Learn were not read, so the third condition above is deferred, not met. The adapter is registered so the code, fixtures and tests are reviewable together, and the owner must read the terms (and `robots.txt`) and record the outcome and the poll interval here before the first Cut release that ships it. The Worker's existing ten-minute cache and identifying User-Agent apply meanwhile. The page text also points programmatic readers to the Windows Updates API in Microsoft Graph, which needs a tenant and credentials; the public page was chosen for that reason.

Decisions taken in review:

- The adapter sets `accept: text/html, application/xhtml+xml;q=0.9, */*;q=0.1`, since both its sources are HTML pages and the Worker's default asks for feeds. The probe did not record its request headers, so the first deploy should be checked once with the Worker's exact User-Agent and `Accept`.
- The scanner caps the first table at 256 KB and walks it with `indexOf`, so unclosed tags are read once and the work is linear, not quadratic. The same holds for the first `<table` and the `<title`, which are found with `indexOf` and a bounded slice, not a regex over the whole body.
- The version is the bare `25H2`, so a Windows 10-only update shows as "Windows 22H2" on the front card; the title keeps 10 or 11. Splitting the family into Windows 11 and Windows 10 is a larger UI change for its own pull request.
- A version is marked "end of updates" only when every edition has ended (Windows 11 23H2 is not, while Enterprise is still serviced). Marking it when any edition has ended is a one-word change (`every` to `some`) if the owner prefers.
- If one of the two pages answers other than 200, the whole source fails and the last good copy is served until it expires. Tolerating one failed page belongs in its own Worker pull request.

## Update: the SteamOS adapter (2026-10-12)

A read-only probe fetched both Steam sources from a GitHub runner on 2026-10-12 and both answered 200: the news API, `https://api.steampowered.com/ISteamNews/GetNewsForApp/v2/?appid=1675200&count=5&maxlength=300` (`application/json`; `appnews.newsitems[]` with `gid`, `title`, `url`, `date` in unix seconds, `feedname`, `tags`), and the RSS feed `https://store.steampowered.com/feeds/news/app/1675200` (`text/xml`; `title`, `link`, `pubDate`, `guid`). The newest posts of both were Steam Client updates, not OS releases, so the first two probes showed no SteamOS post. A third request, `...&count=100&maxlength=1` (200, `application/json; charset=UTF-8`, 43,309 bytes, SHA-256 `fe89ecc361ddb50ef5ba0e16a94f7d315808529a0a9adaf08580473644d1102b`), settled it: SteamOS posts are interleaved with Steam Client posts, and 25 of the 100 items carry `SteamOS` in the title. The probe recorded the title, date and tags of those 25 and cut its excerpt at 4,000 characters, so 19 are complete.

- Source: the adapter `deploy/sources/steamos.js` is registered and fetches that request (`count=100`, so the SteamOS posts are inside the page; `maxlength=1`, so the post text is not sent). The RSS form has a parser (`parseFeed`) but is not on the allowlist, because one failing URL fails the whole source, and the registered `parse` reads the JSON only (the RSS item scanner is not bounded). Posts dated more than a day ahead of the clock are refused. (The 180-day window that followed here is superseded by ADR 0007.) The link is rebuilt from host and path, with no credentials, port, query or fragment.
- Titles: `SteamOS 3.9.2 Beta`, `SteamOS 3.9.1 Preview`, `SteamOS 3.8.28`, and `SteamOS 3.8` once. No build id was seen in a title; the build is empty unless a title carries one such as `20250522.1`.
- Stage, read from the tags as recorded: `stablechannel` marks a stable build, which Valve sometimes also tags `betachannel` and `previewchannel` (`SteamOS 3.8.12`, `3.8.11`), so a stable tag wins. A beta carries `betachannel` and `previewchannel`; a preview carries `previewchannel` alone. Both are `beta`, and the words Beta and Preview in the title give the same answer. A post that names no channel is skipped, not guessed. Moderation tags (`mod_reviewed`, `ModAct_...`) appear on some posts and are ignored; the fixture leaves the real ones out because they embed account and action identifiers.
- Ids: the probe did not record a `gid` or a link for these posts, and none was invented. A release id is the news page with the title as a slug (`.../news/app/1675200#steamos-3.8.28-beta`), the same from the API, the feed or the snapshot, so a snapshot row and the live post never appear twice. The link is the post's own link when it is on `store.steampowered.com` or `steamstore-a.akamaihd.net` (the API's external-post host, added to the Valve hosts in `families.json`), and the Steam Deck news page otherwise, which is the only link the snapshot rows have.
- Fixture: `tests/fixtures/valve/getnewsforapp-steamos-titles.json` holds the 19 complete titles, dates and tags exactly as recorded, in the API's JSON shape; its README says what the probe did not show. The two Steam Client fixtures are the recorded items.
- Snapshot: two rows, the newest stable post (`SteamOS 3.8.28`, 2026-09-25) and the newest beta or preview post (`SteamOS 3.9.2 Beta`, 2026-09-25), from the same recorded data. The Worker's live answer is the 100 newest posts, which reach back to at least June 2026 in the recorded data, inside the dial's 26 weeks.
- Terms of use for automated polling were not checked in the probe; the Worker's cache (10 minutes) and back-off (5 minutes) keep the rate low, and the owner confirms the terms before the next release.
